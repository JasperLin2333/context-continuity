# 交接与并行修改

## 最小交接内容

以下是信息示例，按任务删减，无须每次填表或落盘：

```text
当前目标与授权：这轮要完成什么，可以修改哪些范围。
已采纳决定：决定、适用范围，以及原文或维护源位置。
编辑源与必读路径：接收者实际可访问的位置；摘要不能替代打开源文件。
实际进度：哪些已保存，哪些只是计划，接下来还缺什么。
修改责任：各执行者的范围、共享文件由谁整合。
验证边界：已执行的检查、结果、尚未验证的部分与阻塞。
```

仅在现有协作工具与用户授权允许时发送给其他 Agent 或成员；无发送权限时返回交接内容，不能自行联系他人。跨环境路径不可直接访问时，通过已授权的共享方式提供源文件，并明确版本及尚未同步的部分；不要提供无法访问的本机路径并声称对方已共享上下文。

接收者先核对目标、决定与源正文的差异。摘要过时就修正摘要的理解，不能用摘要覆盖当前源。找不到依据的“已完成”标记回到实际文件或结果核对。

## 并行修改

先按文件或清晰的修改范围分工。相互依赖的共享文件可交给一个整合者串行处理，不必为小任务建立复杂调度。

读取与写入之间存在时间差时：

- 写入前重读受影响内容，核对任务开始时的版本与现有差异。
- 平台支持版本前提时用它拒绝过期写入；哈希或 Git diff 只能帮助发现变化，本身不提供锁。
- 同一区域出现无法判断的业务冲突时保留双方内容与现场，询问必要取舍；不能用覆盖、重置或全仓回滚“解决”。
- 整合后核对所有本轮成果和有效约束，不能只验收最后一个执行者的完成声明。

交接结束或任务完成不自动授予后续发布、删除或持续追踪权限。未完成工作如实说明，不能为了收口修改目标。
