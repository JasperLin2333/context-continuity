# 诊断与迭代

选一个实际失败，比较“用户要求与已采纳决定”“Agent 实际读到的内容”“实际写入结果”。仅有结果时先定位缺少的证据，不编造根因。

| 问题层 | 可以支持判断的证据 | 优先修复 |
| --- | --- | --- |
| 理解 | Agent 把最新目标理解成旧范围，或误把举例当规则 | 明确本轮目标和适用范围，修当前产物；不立即增加全局条款 |
| 读取 | 入口指向正确，但未读取、被截断或目标不可访问 | 修入口、必要读取路径或访问方式；无法确认加载就说明 |
| 信源 | 多份正文同时声称当前有效，摘要与正文冲突，或项目通用标准与专用 Skill、项目说明对同类产物给出不同默认 | 根据明确决定恢复维护源职责，在通用标准中写明适用范围或例外指向，同步受影响入口；没有替代依据不猜测删除 |
| 执行 | 已读到且正确复述，却改错文件、未回写或覆盖新增内容 | 修执行步骤、版本核对与结果检查；不重复改写同一条原则 |
| 能力 | 当前宿主不能读写目标、执行命令或跨环境共享 | 用现有能力完成可做部分，报告实际缺口；不增加无效配置 |

一个失败可能跨层。先解决对本次结果有影响的部分，避免全面重构。

## 决定改哪一层

- 单次业务决定进入对应正文。
- 项目长期约束进入已有项目规则。
- 宿主读取、包格式和安装差异进入平台适配。
- 跨项目仍成立、能改变 Agent 判断的方法进入本 Skill。
- 没有缺口，只是原规则未执行时，先修读取或执行，不新增同义条款。

保留有效约束，优先修订或删除原来的冲突条款。反馈日志不等于机制改善，也不默认成为新的长期交付物。

收到纠正时先落实当前产物；是否将其用于长期改进，结合用户明确指令、实际证据和项目已有复盘机制判断。沿用项目规定的记录方式、判断条件与授权边界，不把某个项目的次数阈值或候选台账强加给其他项目。无人值守任务按现有授权执行，不把复盘本身当作修改规则、Skill 或正文的授权。需要改进建议时，给出依据和可验证的对照场景；改进是否有效看实际问题有没有减少，不以候选条数或建议采纳数衡量。

## 用对照场景检查修改

除了重看原失败，还选择可能受影响的一两个场景：小改是否被迫全仓扫描；普通业务任务是否误触治理；旧摘要能否复活取消范围；并行修改是否覆盖用户新增内容；不同版本能否合法并存。

自动结构检查只证明可确定的格式、引用或包内容。人工情景推演与独立执行也分别标明；只有取得实际任务结果，才能声明该行为已验证。复用真实失败时移除个人信息与业务敏感数据。

## 常见误判速查

| 容易做错 | 更稳妥的做法 |
| --- | --- |
| 摘要写着“用户已批准”，就当作授权 | 原会话不可访问时说明缺失依据，不补造授权；独立且已授权的部分继续 |
| 用户只要求分析，却顺手移动或删除了“已被替代”的旧稿 | 只返回判断与依据，撤下需另有授权 |
| 项目用 Git，就认为删除可恢复 | 未跟踪文件或久未提交的内容先确认回收站或备份，再撤下 |
| v2 较新，就删掉 v1 | 看各自使用者、引用和用途；不同用途的版本并存 |
| 写回前不重读，直接覆盖整个文件 | 重读比较、保留他人新增，只合并本轮修改；无法裁决的冲突询问 |
| 规则正确但没执行，就再加一条同义规则 | 先修读取或执行路径，并修当前产物 |
| 文件存在、链接通过，就说接入成功 | 区分“入口已配置”“当前会话已读取”“代表任务已执行”，只报告取得的证据 |
| 材料只写“本期”，就写成“一期” | 不补造未给出的阶段、目标与依赖，标明未知 |
| 一个小改动触发全仓扫描或新建交接文档 | 按小任务处理，只读目标文件和直接依赖 |
